## 二、0x5AC4C 表几何修正（推翻 docs/09 记录）

docs/09 记作「172 张调度表，步长 16」——两点皆误。实测：**单张 u32 槽偏移表，n=14574（0xE2EE），步长 4**；
「公差 16」是表值序列的性质（每项指向下一 16B 槽），被误读为表步长；「172」来源见下节。
表地址在 img 内**零交叉引用**（绝对/相对 u32 均 0 命中）→ 消费者只能是深层代码或运行时生成码。

槽分类统计（14574 项）：fillA(8b010100×4)=1393、fillB(89010100×4)=682、zero=1339、real=11160。
fill 槽是间隔排列的占位/对齐填充；real 槽为记录数据（含指针与小整数字段），非模板字节码。

## 三、172 记录区（真正的「172」）@0x2CB80..0x2D640

恰为 172 个连续非填充槽（2752B），内容是**记录/描述符**而非可执行表：
- 深码指针 23 个（去重），落点页 0x45/0x4B/0x52/0x59（宿主支撑库区）
- 竞技场自引用指针 42 个（0x2C900..0x2D200 邻区记录链）
- 标签字 0x28/0x8A 共 20 个；长度族 0x2AF9/0x2EE1/0x32C9…（公差 ~0x3E8）42 个
- 半记录跨 16B 槽边界交错（字段位序不固定），完整字段图式未破——留待动态观测

**结论**：docs/09「172 张 PSX→x86 JIT 调度表」是把这簇 172 条数据记录误判为调度表。

## 四、宿主支撑库区证据（0x40560..0x5AC4B）

- 0x598AA：`push ebx/esi/edi` + word 拷贝环 + `0x800` 进位 + `1MB 回绕`（`cmp 0x100000/sub`）——PSX VRAM 半字拷贝例程
- 0x59914：跳过 0x20/0x09 字符——字符串工具
- 0x5185E：`push $0x4e722; jmp rel32`（→0x56254）+ `lea 0x0(%esp),%esp`——MSVC 序言族，深码指针的真实落点
- Ghidra decompiled 存档中 5/12 函数落竞技场、4/12 落本区——深区**确为真 x86 代码**（非模板字节码）

## 五、路线影响（对 H-6a 结论的修正与强化）

1. 修正：img 深区不是「JIT 模板字节码库」，而是**宿主侧支撑库真码**（VRAM/字符串/内存例程）+ 数据竞技场。
2. 强化：入口驱动桩（0x2B7）静态与动态均不引用深区/槽表 → **PSX 模拟/JIT 核心驱动确实不在明文 img 中**，
   与 H-5a 零写入证明合并：该驱动或在主 EXE stub 侧、或需 BIOS 输入触发运行时生成。
3. 纯 HLE 无 ROM 路线维持不可达判定；路线 B'（合法 BIOS ROM）仍是解锁深区执行的唯一已知钥匙；
   路线 C（归档 + DuckStation）成本已因本轮测绘大幅下降（布局已清）。
